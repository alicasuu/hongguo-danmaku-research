## What the native records mean

Both native adapters address `/novel/commentapi/comment/list/{vid}/v1/` on `api5-normal-sinfonlineb.fqnovel.com`. Their body selects `comment_type=20`, `group_type=30`, `group_id=vid` and `business_param.book_id=series_id`. They check `common.group_id` and published `common.status=1`, read `common.content.text`, and interpret `expand.offset_time` (fallback `comment.offset_time`) as milliseconds. Their browser renderer passes the resulting seconds to a danmaku engine bound to the active video element.

This is a materially different source from the ordinary website's `episodeSocialInfo.reviews.reviews`, whose `dm-init-*` identifiers and display timing are generated by the renderer. The code supports a native playback-offset interpretation. The unit and live provenance have not been independently verified against a successful authorized response in this project.

Neither adapter retains message IDs, posting times or raw source JSON in its final display list. Therefore their output cannot establish that those fields exist upstream. Our parser preserves the complete message object and any actual `comment.comment_id`; absent IDs stay NULL. Candidate posting fields stay verbatim in raw JSON and `posting_time_raw_json`; `posted_at` is not populated by guessing epoch units. Offset field path, endpoint, collection time, source and page hash are retained.

## Pagination and research coverage

Both read `extra.next_query_danmaku_list_time` and offsets inside `common_list_info.cursor` (including JSON-encoded cursors). Explicit `has_more=false` terminates pagination. At the reviewed revisions, zfdang forwards the cursor to subsequent requests; redapple extracts its offset but sends an empty request cursor. zfdang allows five consecutive empty pages; redapple allows two. Both cap scans at 40 pages / 3,000 display items and cache successful responses for five minutes. Both deduplicate by rounded playback seconds plus cleaned text, discarding repeated identical messages, and omit text over 200 characters. These are player-display choices, not historical research guarantees.

Our corrected adapter:

- Preserves text and raw fields without display cleaning or truncation.
- Follows both explicit offsets and opaque cursors, preserving cursor strings; terminal false wins. Unknown or non-advancing pagination fails visibly.
- Uses source + episode + native message ID where present. Missing-ID fallback is source + episode + original text + offset + raw posting fields, explicitly labeled `content_offset_raw_time_fingerprint`; distinct identical messages can collapse. It is never a fabricated platform ID.
- Commits messages, immutable versions and page checkpoints atomically. Revisions in raw fields are preserved, including changed likes.
- Resumes only after checking the saved page hash, and reparses the original pagination evidence.
- Begins fresh incremental scans from zero because playback position is not posting time; late arrivals can target old positions.
- Keeps all native coverage partial even after a terminal page. No successful live history scan, completeness denominator or delivery latency has been established.

## Authorized-access finding and live test

The repositories explicitly depend on imitating the official Android client and generating signature headers. Those access mechanisms are outside the user's constraints and were not reproduced.

The existing unsigned `sinfonlinea` probe and the new single-episode `sinfonlineb` probe both returned HTTP 200 with application error `110001` / `unknown error`, not a message list. The new test used drama `7701328280862854168`, episode `7701328426518465561`, one request and no retries, signatures, login credentials or forged devices. Evidence: `output/research_completion/native_b_probe/run_22_page_1.json` and `native_b_result.json`. The generic error does **not** isolate the cause to signatures alone. It establishes only that the tested unsigned request did not provide data.

A final controlled check used the website's actual source duration, 168,554 ms, rather than the unknown-duration value zero. It returned the same 110001 error and zero records. Evidence: `output/research_completion/native_source_duration_probe/run_25_page_1.json` and `native_source_duration_result.json`. This does not determine which other server-side requirements failed.

The supported browser connection did not expose the user's logged-in Chrome session. The accessible website player displayed ordinary-review overlays; its full-comment button handed off to the app. Browser policy blocked that handoff; it was not bypassed. The normal player's media download action failed; a blob URL alone does not establish DRM.

Official-source investigation also checked the [Hongguo creator platform](https://www.shortdramas.com/) and the [Douyin authorized video-data solution](https://open.douyin.com/platform/resource/docs/ability/open-data/video-data-solution). The former offers creator/project services, but no publicly verified native-danmaku export was found. The latter concerns authorized Douyin video data, not a demonstrated Hongguo VOD danmaku endpoint. Livestream interaction APIs are a different data product. No alternative was represented as a working Hongguo research channel.

Needed to unblock: a platform-supported endpoint or rights-holder export for an identified Hongguo episode, with documented playback units, scope and pagination. A native request/response export can be imported without exposing auth headers; provider provenance is an assertion until independently checked. Web login alone has not demonstrated permission or technical access to the app-native pool.

**Actual native records collected: 0.** Expansion to one complete drama or all 10 native pools remains blocked; the code and fixture tests are not a successful proof of concept.

## Video architecture review

The third repository usefully separates episode discovery, URL retrieval, per-episode tasks, retries, partial files, metadata and progress. Its README describes persisted per-series state in `offline_dl.py`; this was reviewed as documentation, not executed. Its documented media acquisition depends on app signing and decryption and is excluded.

The inspected `downloader.py` disables TLS verification, accepts HTTP 200 for segmented ranges, lacks strict Content-Range validation and byte validators, and treats an existing nonempty file as sufficient to skip. A preallocated file's length does not prove every segment downloaded. Its manager's same thread pool runs orchestrators and child jobs, which can exhaust workers when enough series wait on their children. These behaviors were not adopted.

Our optional `--resume-transfers` path uses normal HTTPS with TLS verification, sequential bounded transfers, `.part` checkpoints, URL hashes, strong ETag/Last-Modified with If-Range, exact Content-Range checks, safe restart when Range is ignored, capped transient retries, and no retry on access/rate denials. It does not treat 416 or file existence as completion. FFprobe plus full FFmpeg decode precede publication; an independent expected duration and a full-episode assertion are still required to mark the imported asset complete. Manifest reruns skip transfer only when a file exists, then revalidate it. No direct URL or token is stored in transfer checkpoints.

Transport unit tests use labeled synthetic bytes and mocked verification; existing media tests generate local test videos. **Actual Hongguo full videos collected: 0.** Ten first-episode source durations were collected, but no full-video duration comparison is possible without authorized files.
